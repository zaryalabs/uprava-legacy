# Стек и интеграции: сохранить удачные основы, проверить неизвестное

Снимок: `0.2.26`, commit `9d096834eadfacd9f04a551c5557b33194e7ca4b`.
Дата анализа: 2026-10-03. Здесь разделены опыт владельца, проверяемые свойства
реализации и рекомендации.

## Главный вывод

Владелец положительно оценивает Rust и React. Причиной перезапуска стал темп
расширения продукта и недостаточная доводка сценариев. Замена языка или UI
framework не следует из этого опыта. Сохраняем их как исходный выбор новой
итерации; конкретные версии и зависимости пересматриваем при проектировании.

Отдельное неудобство — долгое ожидание Rust-сборки. Его нужно исследовать как
стоимость цикла разработки. Время компиляции, время полного quality gate и
время сборки контейнеров — разные величины; объединение их под «Rust медленный»
не даёт основания для улучшений. Получен узкий замер повторной проверки
protocol после clippy/test cache: 5.75 с и 0.12 с без изменений. Профиль полной
сборки и типового изменения не получен; условия и ограничения описаны в
[исследовании инструментов](../research/06-tooling-and-build-performance.md).

Источники версий — [Cargo.lock](../../../../Cargo.lock) и
[web lockfile](../../../../apps/web/package-lock.json), прочитанные для указанного
снимка. Диапазоны в manifest не следует принимать за разрешённые версии.

| --- | --- | --- |
| Backend и Node | Rust, edition 2021; объявленный MSRV 1.88; Axum 0.8.9, Tokio 1.52.3 | Один типизированный стек для протокола, процессов и API; требуется управлять стоимостью компиляции и async boundaries |
| Хранение | SQLx 0.8.6, SQLite | Простое локальное развёртывание; ограничения конкурентной записи и восстановление нужно проверять отдельно от возможности будущего Postgres |
| Web | React 19.2.7, TypeScript 5.9.3, Vite 7.3.5 | SPA с существующим Rust API; отдельные контракты клиента и сервера требуют контроля дрейфа |
| Клиентское состояние | TanStack Query 5.101.0 и локальное React state | Кеш серверных проекций и независимые черновики; согласование свежести, событий и буферов остаётся обязанностью приложения |
| Редактор | Monaco 0.53.0, xterm для PTY | Готовые editing/terminal primitives; общий UX зависит от model lifecycle, данных и композиции панелей |
| Tooling | `rmcp` 2.2.0; ToolHive 0.40.0 закреплён в build/runbook | Общий интерфейс инструментов и отдельный runtime; появляются версия протокола, bridge, OAuth и дополнительные эксплуатационные границы |

Архитектурные основания стека сохранены в
[tech-stack](../../../development/tech-stack.md). В частности, отказ от
обязательного Next.js/BFF поддерживал простой путь Web→Core. Это полезная
эвристика для следующего узкого продукта: дополнительный runtime вводится,
когда у него есть измеримая задача.

## Rust: сохраняем стек, исследуем стоимость изменения

[Workspace](../../../../Cargo.toml) содержит шесть members: protocol, logging,
Core, Node, ToolHive bridge и protocol probe. Core/Node/bridge разделяют protocol
и logging. Такое переиспользование облегчает согласованность; изменение общего
контракта также затрагивает несколько потребителей. Этот граф показывает
возможное распространение пересборки, но без timings не доказывает узкое место.

Root manifest использует `resolver = "2"`, задаёт ограниченные features ряда
тяжёлых зависимостей и не задаёт собственных `[profile.*]`. Проверки `make
rust-l` охватывают workspace/all-targets, `make rust-t` — workspace; полный
`make c` дополнительно включает web, dependency audit, документацию и тесты.
Следует сохранить полный gate перед передачей работы, одновременно добавить
ясный путь быстрой проверки конкретного изменения, если профилирование покажет
выгоду. Не следует ускорять процесс за счёт снятия проверок качества.

## MCP и ToolHive: статус — недостаточно опробованы

Владелец не успел получить достаточный практический опыт интеграций. Это
согласуется с [runbook](../../../runbooks/agent-tooling-toolhive-linear.md):
его статус — `ready-for-manual-acceptance`, а автоматический smoke проверяет
health/version и прямо не заменяет OAuth, discovery и реальный tool call.
Наличие интеграционного кода нельзя выдавать за подтверждённую полезность,
равно как отсутствие ручной приёмки — за провал MCP или ToolHive.

Стоит сохранить замысел централизованного управления: Core определяет
доступность и policy; Node наблюдает возможности на месте; вызов оставляет
результат и trace. Progressive discovery через Search→Inspect→Execute
ограничивает заранее раскрываемый объём схем. Цена — дополнительные переходы,
актуальность definition/schema hash и понятная диагностика причин отказа.

Текущий путь имеет отдельный ToolHive service и bounded bridge; OAuth state
живёт в его volume. Docker socket доступен этому service и требует высокой
степени доверия. Пользовательские инструкции OAuth callback, восстановление
после restart и Disconnect создают самостоятельный UX, который надо принять
целиком. Локальное удаление workload не доказывает отзыв разрешения у upstream.

## Что переносим

Переносим положительную оценку Rust/React, границы Core/Node и идею управляемых
инструментов. Схемы хранения, версии библиотек, граф crates и ToolHive topology
остаются кандидатами на повторное использование. Для каждого важнее небольшой
реальный сценарий с ошибками и восстановлением, чем формальное наличие API.
Готовность интеграции означает понятное подключение, успешный вызов,
предсказуемый отказ, восстановление и отключение без утечки credentials; только
после этого разумно добавлять следующий connector.
