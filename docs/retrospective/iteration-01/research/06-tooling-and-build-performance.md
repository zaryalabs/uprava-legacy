# Инструменты и скорость разработки

Дата проверки первичных источников: 2026-10-03. Локальный baseline — `0.2.26`,
commit `9d096834eadfacd9f04a551c5557b33194e7ca4b`. Это исследование применимых
подходов и план проверок; реальный MCP OAuth flow и сравнительная оптимизация
сборки в данной работе не выполнены.

## MCP: версию контракта необходимо выбирать явно

Официальный `latest` на дату проверки указывает на
[MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).
Ревизия меняет модель протокола: self-contained запросы несут версию и
capabilities; `server/discover` служит обнаружению возможностей. Это свойство
интеграционного протокола, а не требование превращать живой агентский чат в
независимые one-shot запуски.

[Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
показывает существенные отличия от `2025-11-25`: удалены protocol sessions и
initialize handshake, изменён поток уведомлений, tasks вынесены в расширение.
Повтор запроса после разрыва потока требует отдельной семантики побочных
эффектов. Следствие для Uprava: фиксировать совместимую комбинацию client,
SDK, proxy и upstream; не считать обновление одного SDK доказательством
совместимости всей цепочки.

В текущем [workspace](../../../../Cargo.toml) `rmcp = 2.2.0` закреплён точно.
Новая ревизия не была проверена с этой реализацией. Для следующего прототипа
нужна маленькая таблица: поддерживаемая версия, discovery, вызов, error,
progress, cancellation, повтор после disconnect и источник identity. Поведение
неподдерживаемой возможности должно быть явным.

## ToolHive: отделить возможности платформы от нужного среза

Этот обзор дополнен [разбором реализации ToolHive](09-toolhive-control-implementation.md)
на commit `3ca3c8f71152ad6e109dbb881be13ceb17a2cf3c`. Там прослежены
registry/runtime, list/call admission, identity, OAuth, retry, stop и trace;
рекомендации для нашей архитектуры сведены в
[контракты удалённых агентов и tools](10-remote-agents-and-tools-for-v2.md).
Современный source snapshot отдельно от исторического pin Uprava `0.40.0`.

В актуальной [документации ToolHive](https://docs.stacklok.com/toolhive/)
разделены runtime, registry и gateway; доступны CLI и Kubernetes-путь.
[Authorization reference](https://docs.stacklok.com/toolhive/reference/authz-policy-reference)
описывает проверку principal/action/resource и политики для MCP-операций.
Это полезные точки сравнения с нашей централизованной policy, но наличие
возможности в документации не подтверждает её применение в Uprava.

Uprava закрепляет `0.40.0`. [Release notes этой версии](https://github.com/stacklok/toolhive/releases/tag/v0.40.0)
прямо описывают поддержку vocabulary новой MCP-ревизии как подготовительную,
ещё не подключённую к proxy routing. На дату проверки latest release —
[v0.51.4](https://github.com/stacklok/toolhive/releases/tag/v0.51.4).
Это граница проведённого обзора, а не рекомендация автоматически обновлять
production runtime.

Для первой интеграции выбрать один read-only инструмент и сравнить минимальный
прямой MCP client с ToolHive-путём в изолированном тестовом окружении. В обоих
вариантах policy остаётся в control plane; прямой путь служит экспериментом,
а не разрешением обойти Core или незаметно заменить текущий bridge. Измерять
не только время вызова, но и время подключения, число ручных шагов,
диагностируемость отказа и стоимость эксплуатации.

Полезный протокол уже есть в
[runbook](../../../runbooks/agent-tooling-toolhive-linear.md):
Connect → discovery → Search → Inspect → Execute → restart → отказ →
Disconnect/Reconnect. Дополнить его проверкой запрета конкретного инструмента,
изменения схемы и версии протокола. Использовать тестовые данные; не сохранять
tokens и OAuth URLs в evidence. Завершение — один воспроизводимый успешный
цикл и ожидаемые отказы без скрытого fallback. До этого статус интеграции
остаётся «не принята в использовании».

## Rust: сначала измерить путь изменения

[Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html)
показывает длительность compilation units, concurrency и зависимости
критического пути. Такой отчёт позволяет различить тяжёлую зависимость,
codegen и последовательность ожиданий. Он не объясняет время web-тестов или
Docker image build.

В текущем [Makefile](../../../../Makefile) `make c` включает форматирование,
lint, dependency/config checks и тесты нескольких стеков. Для повседневной
работы используется `make l`. Узкой цели для Cargo timings нет; диагностическая
команда ниже обоснованно выполнялась напрямую, без изменения обычного workflow.

### Выполненные замеры

Окружение: macOS, target `aarch64-apple-darwin`, Cargo/rustc `1.93.1` Homebrew; rustc
`01f6ddf75` от 2026-02-11. Workspace и cache не очищались.

```sh
/usr/bin/time -p cargo check --locked --offline -p uprava-protocol --timings
```

Первая попытка завершилась с exit `101` до компиляции: Cargo не смог распаковать
`autocfg 1.5.1` в registry cache из-за файлового sandbox (`Operation not
permitted`). `real 0.16 s` — время неуспешного старта, **не время сборки**.
Это ограничение среды измерения, а не дефект проекта.

После разрешённого доступа к cache команда успешно выполнена дважды подряд
без изменения исходников, 2026-10-03 в 18:03 по Москве. К этому моменту уже
завершились clippy и Rust-тесты; перед запуском проверено завершение Vitest и
тестов Generated UI Builder. Наши frontend-тесты параллельно не выполнялись;
посторонняя системная нагрузка не контролировалась. Оба прогона используют
`dev` profile и существующий cache, поэтому первый прогон **не cold build**.

| Последовательный прогон | Wall time (`time`) | Время Cargo | Fresh / dirty units | Max concurrency |
| --- | --- | --- | --- | --- |
| 1, после clippy/test cache | 5.75 s | 5.72 s | 48 / 1 | 1 |
| 2, без изменений | 0.12 s | 0.11 s | 49 / 0 | 0 |

Оба прогона завершились с exit `0`; Cargo указал 49 units, `jobs=12`, `ncpu=12`.
Единственная выполненная compilation unit первого прогона —
`uprava-protocol 0.2.26`, 5.52 s по HTML timings. Отчёты имеют идентификаторы
`20261003T150320.429794Z` и `20261003T150332.470725Z`; компактный результат
сохранён здесь, полный HTML остаётся локальным build artifact.

Результат подтверждает повторное использование cache для этой узкой проверки.
Он не измеряет полную компиляцию/линковку продукта, типичную правку Core/Node
или ускорение после оптимизации. Причина исходной жалобы на долгую сборку
остаётся непроверенной; вывод о смене стека из этих чисел не следует.

### Следующий ограниченный эксперимент

В отдельном checkout измерить небольшое изменение leaf crate и изменение
protocol. Отдельно измерить `cargo build` и один целевой тест; перед сравнением
оптимизаций повторить одинаковый контрольный прогон на том же cache.
Зафиксировать toolchain, platform, features, profile, cache state, wall time,
число пересобранных units и наиболее долгие units. Для cold baseline применять
отдельный `CARGO_TARGET_DIR`, сохраняя обычный cache; не выполнять `make clean`
в рабочем дереве ради сравнения.

Затем менять только один фактор: объём debug info, выбранные dependency
features, повторные версии или границу crate. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)
позволяют отдельно управлять dev/test настройками; incremental по умолчанию
включён для dev и применяется к workspace/path dependencies.
[Cargo features](https://doc.rust-lang.org/cargo/reference/features.html)
объясняет объединение features и возможные повторные сборки при resolver 2.
Уменьшение диагностической информации имеет цену при отладке; дробление crates
добавляет публичные границы. Принимать изменение только при повторяемом выигрыше
на типовом рабочем действии и сохранённом полном gate.

Связанный [реестр экспериментов](experiments.md) должен хранить результаты
отдельно от этих гипотез. Смена Rust или React не является исходной целью.
