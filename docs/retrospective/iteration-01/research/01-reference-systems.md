# Референсные системы: T3 Code и OpenCode

Дата чтения источников: **2026-10-03**. Это исследование первичной документации
и выбранных участков исходного кода, а не сравнительный пользовательский тест.
Начальный обзор дополнен разбором закреплённых исходников:
[T3 Code](07-t3-remote-agent-implementation.md),
[OpenCode](08-opencode-agent-tooling-implementation.md) и
[ToolHive](09-toolhive-control-implementation.md). SHA и ссылки на конкретные
функции сохранены там и в [sources.md](sources.md). Ниже остаётся обзор
архитектурных идей; подробные решения для переноса находятся в
[рекомендациях по удалённым агентам и tooling](10-remote-agents-and-tools-for-v2.md).

## Зачем выбраны эти системы

T3 Code полезен как пример клиентской оболочки над агентскими runtime с
разделением исполнения и интерфейса. OpenCode полезен как альтернативная
организация самого агентского сервиса. Сравнение позволяет отделить качество
панели управления от возможностей провайдера. Оно не устанавливает, какая
система быстрее, безопаснее или удобнее: общих измерений нет.

Новая цель Uprava — довести ежедневный цикл «подключиться к облачному агенту,
задать работу, наблюдать, вмешаться, вернуться позже». Поэтому ценность
референса определяется тем, как он помогает этому циклу, а не количеством
его функций. Разбор проведён после чтения текущего
[README Uprava](../../../../README.md) и
[Managed runtime runbook](../../../runbooks/managed-agent-runtime.md):
baseline `0.2.26` уже содержит live runtime, approvals и восстановление.

## T3 Code: полезные границы

В [архитектурном описании](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/docs/internals/overview.md)
процессы провайдеров, терминалы, Git и файлы принадлежат серверу окружения.
Клиенты используют RPC, а общая логика соединения и состояния вынесена в
`packages/client-runtime`. Возможности независимо обновляемых клиентов и
серверов согласуются через capabilities. Это документированное намерение
архитектуры; весь сервер на соответствие этим правилам не аудировался.

Для Uprava полезен сам принцип владельца исполнения. Его естественное
отображение — Node владеет процессом и workspace, Core владеет политиками и
пользовательским состоянием. Переносить прямое соединение каждого браузера со
всеми нодами не требуется: это изменило бы принятые границы control plane и
усложнило бы отзыв доступа.

[Connection runtime](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/docs/internals/connection-runtime.md)
отделяет здоровье транспорта от актуальности проекций. Повторными соединениями
управляет один supervisor на окружение; offline и ошибки авторизации не
вызывают бесконечный retry. Кеш остаётся читаемым, а загрузка истории не
тождественна установлению соединения. Такой подход даёт полезную модель для
интерфейса Uprava: «соединено», «история догружается» и «runtime доступен»
должны быть разными признаками.

Выборочно прочитан
[код supervisor](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/packages/client-runtime/src/connection/supervisor.ts):
в нём есть проверка живого соединения при возвращении приложения и отдельная
ветка замены соединения после длительной приостановки. В
[коде thread state](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/packages/client-runtime/src/state/threads.ts)
просмотрены восстановление через `afterSequence`, сохранение согласованной
пары данных и cursor, отбрасывание устаревшей страницы истории. Это
подтверждение существования механизмов в прочитанном коде; тесты проекта
не запускались, покрытие всех гонок не доказано.

Вывод для Uprava: даже узкий чат требует самостоятельного владельца
синхронизации вне React-компонентов. При этом переносить весь пакет T3 и его
набор платформ преждевременно. Достаточно сначала одного web-клиента, одного
Core и проверяемого контракта snapshot/replay.

## T3 Code: ограничения безопасности и адаптеров

[Environment authentication](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/docs/internals/environment-auth.md)
различает авторизацию окружения и облачного relay; успешный WebSocket upgrade
не заменяет проверку scope каждого RPC. Одновременно проект там не является
песочницей: `orchestration:read` допускает чтение доступных серверному аккаунту
файлов, включая пути вне проекта. Это сознательная граница конкретного
продукта, которую нельзя считать подходящей для изоляции клиентов Uprava.

Рекомендация для новой итерации: выбрать единицу доверия до реализации
удалённого доступа. Если два workspace принадлежат разным доверенным зонам,
общий daemon user и проверка пути в UI не создают достаточную изоляцию.
Необходимы принудительные ограничения на стороне исполнения и отдельная
проверка межпроектного доступа.

[Provider constraints](https://github.com/pingdotgg/t3code/blob/ce90eec1ffc2087395227a610843091f4b260cf7/docs/internals/providers.md)
показывает цену унификации провайдеров: адаптер различает driver и конкретный
instance аккаунта, а для OpenCode 1.x и 2.x используются разные схемы
процессов. Документ также объясняет, почему проектные постоянные approvals
нельзя автоматически выдавать для одной supervised-сессии. Для Uprava это
аргумент сначала довести один провайдер, сохранив явную границу адаптера.
Общий интерфейс должен сообщать отсутствие возможности, а не имитировать её.

## OpenCode v2: общий сервис и явные контракты потоков

Этот раздел пересказывает документацию v2. Чтение commit
`907b3bc518fa48e90e8ec24dd327d13eee71c36c` выявило одновременно legacy
`packages/opencode` и новый `packages/core`/`packages/server` с разной
степенью готовности. Реализованная синхронизация remote workspace в legacy
и новый SessionV2 не считаются одним готовым runtime. Различия и явные
`OperationUnavailable` разобраны в [source review](08-opencode-agent-tooling-implementation.md).

[CLI v2](https://opencode.ai/v2/docs/cli) описывает общий background server
пользовательского аккаунта: ему принадлежат sessions, configuration,
integrations, permissions и выполнение tools. Есть отдельные способы запуска
интерактивного клиента, автоматизации через `run` и private server.
Само наличие процесса-сервера ещё не показывает качество удалённого UX.

В [Web v2](https://opencode.ai/v2/docs/cli/web/) описаны интерфейс того же
сервера, локальный bind по умолчанию, защита паролем и pairing с одноразовой
ссылкой. Это удобный референс начального подключения. Его модель одного
пользовательского аккаунта не подтверждает готовность к разделению
недоверенных арендаторов; соответствующий аудит здесь не проводился.

[API v2](https://opencode.ai/v2/docs/api) различает два вида потока:
`/api/event` — volatile, с потерей событий при отключении и ошибкой при
переполнении медленного потребителя; experimental session log читает события
после sequence и умеет продолжить live-поток. Документация также предоставляет
session-scoped permissions и interrupt. Поэтому вывод «HTTP/SSE мешают
реактивности» неверен. Определяющим является договор о состоянии и
восстановлении, а не название транспорта.

## Что переносить в замысел Uprava

| Наблюдение | Рекомендация для узкого первого среза | Как проверить |
| --- | --- | --- |
| У исполнения и синхронизации есть явные владельцы | Сохранить Core/Node, выделить клиентскую модель соединения | Reload и второй клиент видят тот же run без повторного запуска |
| Соединение и свежесть данных различаются | Показывать достоверный статус и читаемую историю offline | Разрыв сети не превращает старую проекцию в «актуальную» |
| Replay нуждается в отдельном контракте | Хранить cursor вместе с применённой проекцией | Replay и live-события не дублируют сообщения |
| Провайдеры различаются по процессам и полномочиям | Один качественный адаптер, capability gate для остальных | Неподдерживаемая операция получает явный отказ |
| Организационный project не всегда sandbox | Зафиксировать свою границу доверия и проверять её на Node | Пользователь другого workspace не читает файл и не отвечает на approval |

Пока не стоит переносить масштабную многоплатформенность, весь каталог
провайдеров, relay-инфраструктуру и сложные secondary workflows. Это
рекомендация о последовательности: идеи остаются доступными, но каждая должна
заслужить место в первой версии измеримой пользой.

Следующий шаг — воспроизводимый сценарий на зафиксированных версиях двух
систем и Uprava. Нужны одинаковые условия сети, размер истории, провайдер и
набор действий. До этого оценки «лидер», «production-ready» и «быстрее» были
бы предположениями.
