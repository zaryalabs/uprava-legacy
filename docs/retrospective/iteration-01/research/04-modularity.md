# Модульность и композиция расширений

Рекомендация: сохранить маленькое ядро с явным владением состоянием и проверить
модульность на нескольких независимых расширениях до проектирования большой
plugin ecosystem. Желание приблизиться к Vim трактуется как программируемость
и композиция действий. Язык расширений, способ упаковки и степень свободы UI
пока не выбраны.

Исследование выполнено по первичным документам, прочитанным 3 октября 2026
года. Сравнительный performance benchmark Neovim и VS Code не проводился.
Текущий механизм Uprava разобран отдельно в
[ретроспективе решений](../retrospective/03-decisions-and-modularity.md).

Дополнение от 7 октября: [разбор модульности DeepSeek Harness](11-deepseek-harness-modularity.md)
даёт конкретные механизмы service dependencies, scoped registrations,
resource ownership, preset revisions и client replacement. Он становится
основным implementation-референсом этой области. Neovim сохраняется как
ориентир композиции действий, VS Code — размещения и изоляции расширений.
Перенос в Core/Node и developer tools описан в
[рекомендациях Harness для v2](13-deepseek-harness-for-v2.md).

## Полезные свойства референсов

[Neovim API](https://github.com/neovim/neovim/blob/master/runtime/doc/api.txt)
предоставляет внешним клиентам и плагинам функции, события и типизированные
объекты вроде buffer/window/tabpage. Metadata описывает версии API;
совместимость публичных функций и событий имеет отдельные правила. Отсюда
полезный для Uprava принцип: действие и объект должны иметь программный
контракт, доступный нескольким интерфейсам. Это не доказательство sandbox
безопасности плагина и не требование переносить event loop редактора целиком.

[VS Code Extension Host](https://github.com/microsoft/vscode-docs/blob/main/api/advanced-topics/extension-host.md)
разделяет local, browser и remote execution расширений; место исполнения
зависит от runtime и требуемых ресурсов. Activation events позволяют загружать
расширения по необходимости. Для Uprava полезно различать UI-часть рядом с
пользователем и workspace-часть рядом с файлами. Process isolation помогает
ограничивать влияние отказа, но сама по себе не определяет полномочия
расширения.

## Что означает композиция для Uprava

Предлагаемые свойства, которые следует проверять на прототипе:

- Именованная команда вызывается из кнопки, palette, hotkey и agent tool через
  один application contract. Идентичность вызывающего и policy проверяются
  для каждого входа.
- Адресуемый объект имеет stable reference и тип. Plugin получает разрешённое
  представление, а не указатель на внутреннее состояние Core или React.
- Событие сообщает о подтверждённом изменении. Extension не меняет durable
  state обходным путём.
- Сервисы расширений имеют версию, capability requirements, deadlines и
  правила отмены. Ошибка или отсутствие расширения даёт понятный fallback.
- Пользователь может настроить сочетания действий без изменения ядра, но
  конфигурация не расширяет его права.
- Отключение и обновление освобождают subscriptions, процессы и ресурсы;
  сохранённые артефакты остаются читаемыми хотя бы в базовом виде.

Пример минимального контракта для проектирования, **не текущий API Uprava**:

```text
Command: trace.open
Input: TraceRef
Required capability: trace.read
Context: caller, project, workspace, session
Result: ViewDescriptor | typed error

Renderer: trace.summary
Input: permitted TraceSnapshot
Fallback: plain text summary with source references
Lifecycle: activate, subscribe, cancel, dispose
```

Этот пример связывает trace как сохранённую идею с проверкой будущей
расширяемости. Внешний модуль не получает SQL access, глобальную карту токенов
или произвольную возможность вызывать Node.

## Варианты архитектуры

Оценки ниже — наше сравнение применимости, не измеренные рейтинги продуктов.

| Вариант | Польза | Цена и ограничение | Когда применять |
| --- | --- | --- | --- |
| Bundled modules и явные contributions | Простые типы, сборка и контролируемая поставка | Новые возможности требуют релиза приложения; ограниченная пользовательская программируемость | Первый продукт и проверка границ |
| Скрипты внутри основного процесса | Быстрая композиция и простая связь с runtime | Блокировки, ошибки и права оказываются близко к ядру | Только при явной модели доверия и доказанном сценарии |
| Отдельный extension host с RPC | Версии контрактов, control над ресурсами, локальное/удалённое размещение | Serialization, lifecycle, диагностика и поддержка совместимости | Недоверенные или независимо поставляемые расширения |

Рабочее предложение с учётом Harness: начать с первого варианта с явными
сервисными зависимостями, lifecycle owners и observable activation.
Bundled implementation не должна означать отсутствие публичного контракта
композиции. Отдельный extension host проектировать на границе, которую
действительно нужно открывать. Не вводить
универсальную VM, собственный язык или marketplace раньше доказанной пользы.
Это сохраняет возможность большей модульности, не делает её новой причиной
распыления.

## Проверка достаточности контрактов

Два контрастных расширения выявляют больше, чем несколько тем оформления:

1. Trace viewer регистрирует команду, показывает разрешённые данные, получает
   обновления и сохраняет plain-text fallback после отключения.
2. Read-only capability inspector получает scope конкретной ноды и показывает
   причины недоступности tool. Запрос к чужой ноде отклоняется независимо от UI.

Критерий успеха: расширения используют публичные contracts без feature-specific
ветвей в Core dispatcher, transport или shell; поддерживают cancellation и
отключение; не могут повысить права. Затем проверяется конфликт двух
contributions и несовместимая версия API.

Существующие тесты bundled theme и contribution resolution проверяют более
узкую модель. Их прохождение не доказывает описанную будущую композицию.
Статус проверок и оставшееся задание приведены в
[экспериментах](experiments.md). Решение о полноценном extension host принимается
после такого опыта, а не по внешнему сходству с Vim.
