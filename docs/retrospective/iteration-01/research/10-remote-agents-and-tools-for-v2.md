# Что перенести во вторую итерацию: удалённые агенты и инструменты

Рекомендация по результатам чтения реализаций: сохранить разделение Core/Node
и собственные durable-контракты Uprava, а у T3 Code, OpenCode и ToolHive взять
отдельные механизмы управления соединением, сессией и инструментами. Первый
продуктовый срез — один удалённый агент, управляемый через живой чат, и один
внешний инструмент с понятными правами, состоянием и отзывом доступа.

Дата исследования — **2026-10-03**. Это проектные рекомендации, а не уже
принятые ADR или реализованная архитектура второй итерации. Основание —
закреплённые исходники и прочитанные тесты:

| Реализация | Изученная ревизия | Подробный разбор |
| --- | --- | --- |
| T3 Code | `ce90eec1ffc2087395227a610843091f4b260cf7` | [Удалённое окружение и provider adapters](07-t3-remote-agent-implementation.md) |
| OpenCode | `907b3bc518fa48e90e8ec24dd327d13eee71c36c` | [Session runtime и tooling](08-opencode-agent-tooling-implementation.md) |
| ToolHive | `3ca3c8f71152ad6e109dbb881be13ceb17a2cf3c` | [Runtime инструментов и enforcement](09-toolhive-control-implementation.md) |
| Uprava | `9d096834eadfacd9f04a551c5557b33194e7ca4b`, `0.2.26` | [Сохранённая архитектура](../retrospective/02-architecture-and-runtime.md) |

Upstream-приложения в этом углублённом исследовании не запускались.
Наличие механизма в коде подтверждает возможность заимствовать подход;
производительность и пригодность целого deployment из этого не следуют.

Дополнение от 7 октября — [DeepSeek Harness для v2](13-deepseek-harness-for-v2.md).
Он уточняет модульность, developer tools и trace. Его SSH capabilities и
native subagent adapters отдельно сопоставлены с нашим постоянным runtime;
контракты Core/Node из этого документа сохраняются.

## Три разных интеграции

**Подключить агентский runtime** — управлять native thread, turn, approvals,
input, interrupt и восстановлением конкретного провайдера. Модель сама
решает, какие инструменты вызвать; Uprava управляет жизненным циклом и
допустимыми границами. Основной референс здесь — адаптеры T3 Code.

**Предоставить агенту инструмент** — объявить схему, проверить identity,
разрешения и аргументы, выполнить вызов, вернуть результат. MCP обслуживает
эту границу. Он сам по себе не предоставляет журнал диалога, управление
turn и восстановление агента. Здесь полезны OpenCode tooling и ToolHive.

**Реализовать собственный агентский цикл** — выбирать модель, собирать
контекст, исполнять tools, обрабатывать compaction и продолжать генерацию.
OpenCode даёт материал и для этого, но такой цикл не нужен первому срезу
панели. Его копирование сразу вернуло бы прежнюю проблему роста scope.

Так же следует различать местоположение. «Удалённый агент» для браузера
может быть процессом на Node, к которому Node обращается по локальному
transport. «Удалённый MCP» — отдельный внешний сервис, к которому требуется
ещё одна identity и политика доступа. Эти адреса и credentials нельзя
объединять в одно поле «подключение».

## Границы, которые стоит сохранить

| Компонент | Предлагаемая ответственность во второй итерации |
| --- | --- |
| Core | Пользовательская identity, допуск Node, session и routing, durable commands/events, policy, tool grants и отзыв доступа |
| Node | Workspace, provider process, adapter, локальные ограничения, доставка событий, фактическое состояние runtime и инструментов |
| Provider adapter | Native protocol и version/capability handshake, thread/turn mapping, approvals/input, cancellation, восстановление поддерживаемым способом |
| Tool runtime | Соединения с MCP upstream, запуск локального workload при необходимости, transport, upstream authentication и локальное enforcement |
| Client runtime | Подключение к Core, восстановление проекций, cursor и cache; React получает готовое состояние и отправляет команды |

Из T3 переносится явное владение окружением и адаптерами, но его топология
не обязана становиться нашей. Браузер продолжает работать через Core.
Для Node за NAT разумный кандидат — инициируемый Node исходящий защищённый
control channel; пользовательская сессия браузера не превращается в
credential для Node или provider. Выбор транспорта не отменяет проверки
каждой команды и fencing устаревшего соединения.

Проект и путь workspace остаются логическими объектами. Если процессу
доступны чужие файлы или сеть, metadata проекта и скрытая кнопка в UI не
изолируют исполнение. Единицу изоляции нужно выбрать под первый deployment:
например, выделенная Node для одного доверенного оператора или отдельный
изолированный runtime для workspace. Это отдельное решение от выбора MCP.

## Цепочка 1: принятие команды и работа удалённой сессии

Предлагаемый путь:

```text
Web: input_id + session_id
  → Core: авторизация + durable command/receipt
  → Node: проверка поколения и дедупликация command_id
  → adapter: native turn/start
  → provider: delta / tool / approval / completion
  → Node outbox → Core event + projection → client runtime
```

Из нового runtime OpenCode полезен принцип **сначала принять input в
хранилище, затем разбудить исполнителя**. Повтор с тем же identity и тем же
содержимым должен возвращать существующий результат принятия; повтор с
другим содержимым — конфликт. Это защищает кнопку отправки от потери ответа
и повторной доставки. Это ещё не гарантия однократного внешнего эффекта.

Из T3 полезно разделение durable orchestration и работы provider adapter.
События пользовательского turn, его принятие провайдером и последующая
финализация результатов должны быть различимы. Внутренний worker не обязан
удерживать HTTP-запрос пользователя до конца генерации.

У legacy remote-workspace OpenCode есть ещё полезный механизм: ответ
удалённого сервера несёт `x-opencode-sync`, а управляющий proxy ждёт, пока
локальная проекция догонит указанную sequence. Для Uprava стоит перенести
сам контракт read-your-writes: receipt команды и подтверждение видимости
её результата — разные этапы. Можно вернуть клиенту sequence для ожидания,
не копируя конкретный HTTP-заголовок или блокировку proxy. Таймаут ожидания
проекции не должен повторно запускать уже принятую команду.

В Uprava уже есть [command/event persistence](../../../../crates/uprava-server/src/persistence/event.rs)
и [Node execution](../../../../crates/uprava-node/src/runtime/application/execution.rs).
Их следует оценивать для переноса вместе с тестами, сохраняя commit-before-
publish и deduplication. Новый frontend не должен заставлять переписывать
эти гарантии с нуля.

Из T3 полезна также сериализация публикации после commit. Сами транзакции
не исключают гонку, когда два обработчика публикуют уже сохранённые события
в обратном порядке. Наш outbox/drainer и клиентская проверка sequence должны
сохранять порядок и при конкурентных командах, а не только в одном потоке.

Минимально нужны разные identity:

| Identity | Для чего нужна |
| --- | --- |
| `session_id` | Долговечный пользовательский диалог |
| `runtime_attempt_id` | Одна жизнь provider runtime; меняется после потери/пересоздания |
| Поколение соединения Node | Старое соединение не принимает новые команды и не подменяет actual state |
| `input_id` / `command_id` | Повтор доставки пользовательского намерения и команды |
| Native thread/turn/request ID | Корреляция с provider, хранится внутри adapter boundary |
| `interaction_id` | Конкретный запрос approval/input с попыткой и сроком жизни |
| `event_sequence` | Порядок и восстановление проекции; не identity команды |

Это предложение контракта, а не требование завести отдельную таблицу на
каждое имя. Важно не пытаться одним native thread ID заменить все роли.

### Approval и interrupt

Approval следует хранить как отдельный запрос со scope, типом действия,
attempt и состояниями requested/resolving/resolved/expired. Разрешение одного
вызова не должно незаметно становиться постоянным разрешением для проекта
или аккаунта. Provider-native approval и Core tool policy отвечают на разные
вопросы; одобрение в одном слое не отменяет запрет в другом.

В Uprava [resolve_provider_interaction](../../../../crates/uprava-server/src/runtime/application/coordination.rs)
уже проверяет текущий attempt и expiry, переводит interaction в resolving
вместе с записью команды. Это сохраняемая основа. У адаптера нужны явные
возможности: поддерживает ли он session-scoped approval, steer, interrupt,
resume, изменение tools между turn. Неподдерживаемый режим должен быть виден
Core и UI до действия пользователя.

Interrupt требует отдельного пути управления: он не может ждать очереди
обычных сообщений за тем turn, который должен остановить. Но успешная
отправка interrupt ещё не означает завершение команды или откат уже
выполненного внешнего действия. UI должен различать «запрос остановки принят»
и подтверждённое terminal state.

## Цепочка 2: возвращение в сессию и неопределённый результат

У T3 стоит взять самостоятельный connection supervisor и разделение
transport health, data freshness и provider health. У OpenCode — durable
session log как источник восстановления и уведомление лишь как повод
перечитать новые записи. Это совместимые идеи, хотя реализация хранилища и
протокола у проектов различается.

Для Uprava предлагается один авторитетный поток пользовательской проекции
из Core. Node может иметь собственную последовательность событий для
надёжной доставки, а provider — native log; клиент не должен самостоятельно
сливать три потока без правил порядка и дедупликации.

1. Клиент получает согласованные snapshot и cursor одной проекции.
2. Подписывается/догружает события после cursor по контракту без окна потери.
3. Применяет последовательные события и сохраняет cursor вместе с данными.
4. При gap, смене поколения или несовместимом snapshot делает resync.
5. Ответы старой загрузки не перезаписывают более новое состояние.

Потеря Web→Core соединения допускает replay. Потеря Core→Node соединения
требует сверки фактического состояния. Потеря provider process требует
поддерживаемого resume либо нового attempt. Это разные процедуры.

Текущая [reconcile_managed_attempt_descriptors](../../../../crates/uprava-node/src/runtime/managed_provider.rs)
честно переводит живо выглядевший descriptor после Node restart в `Lost`:
loopback app-server нельзя безопасно присоединить только по сохранённым
данным. Этот факт не следует скрывать обещанием «автоматический reconnect».

Особый случай — удалённый write-tool выполнил действие, но ответ потерялся.
Повтор только потому, что пришёл timeout, может создать второй эффект.
Рекомендация: хранить идентификатор вызова и состояние неопределённого исхода;
автоматический повтор разрешать лишь при доказанной идемпотентности upstream
или возможности проверить результат. Ни outbox, ни WebSocket, ни MCP сами
по себе не дают exactly-once для внешнего сервиса.

## Цепочка 3: выдача инструментов и конкретный вызов

Для каждого инструмента полезно различать три состояния:

- **Definition:** что это за действие, его схема, источник и версия.
- **Availability:** доступен ли backend сейчас на этой Node и с этой identity.
- **Grant:** разрешено ли этой сессии выполнить это действие в данном scope.

OpenCode полезен материализацией набора tools и проверкой, что вызов относится
к актуальной привязке инструмента. ToolHive полезен отдельными проверками
`tools/list` и `tools/call`. Из этого следует конкретный контракт Uprava:

```text
Core: выбрать tools для session и разрешённого workspace
  → создать binding: tool + schema/version + source + policy generation
  → adapter: объявить provider только поддерживаемый набор
  → call: заново проверить binding, identity, grant и actual state
  → Core native tool ИЛИ Node → tool runtime → upstream
  → bounded result/artifact + redacted trace + terminal/uncertain state
```

Список, выданный модели, полезен для ограничения контекста и UX. Enforcement
остаётся на пути вызова: инструмент мог исчезнуть, grant мог быть отозван,
схема или credential могли измениться после discovery.

### Конкретный пробел в текущем контракте

В `0.2.26` [ExecuteToolRequest](../../../../crates/uprava-protocol/src/tooling.rs)
содержит scope, tool ID и arguments; выбранной агентом версии схемы или
binding ID в нём нет. Core при вызове загружает актуальную definition и
сохраняет snapshot. [persist_session_tool_snapshot](../../../../crates/uprava-server/src/runtime/application/tooling.rs)
обновляет запись при конфликте пары session/tool. Это полезный след, но
не равнозначно проверке «агент вызывает именно ту схему, которую ему
объявили раньше».

Предлагается добавить versioned binding или ожидаемый schema hash в
agent-facing contract и отклонять устаревший вызов с требованием обновить
discovery. При этом trace конкретного вызова хранит использованную версию,
а policy проверяется по актуальному состоянию: старый snapshot не должен
продлевать отозванное разрешение. Изменение потребует миграции протокола и
адаптеров; простого нового поля в UI недостаточно.

### Native, managed и external tools

Нужно сохранить существующее различие managed tools и observed capabilities.
Встроенные shell/files/git провайдера нельзя выдавать за действия, полностью
управляемые Tool Registry Uprava. MCP policy контролирует только проходящие
через неё вызовы. Если агент может обойти её через shell, прямую сеть или
credentials в окружении, ограничение должно действовать на уровне исполнения.

Для небольшого первого набора tools допустимо прямое объявление схем через
поддерживаемый provider adapter/MCP. При росте каталога полезен существующий
подход search → inspect → execute. Но meta-tool обязан проверять настоящее
вложенное имя и binding инструмента тем же способом, что и прямой вызов;
policy только на имени `execute_tool` была бы недостаточной.

Не требуется сразу переносить весь dynamic registry, plugin framework и
все integrations. Достаточно стабильного контракта одного tool и прозрачной
диагностики: не установлен, нет credential, запрещён, схема изменилась,
upstream недоступен, вызов выполняется, исход неизвестен.

## Credentials, отзыв и роль ToolHive

Сохраняемый механизм Uprava — scoped MCP lease. В
[issue_mcp_access_lease_with_state / validate_mcp_access_lease](../../../../crates/uprava-server/src/runtime/application/tooling.rs)
уже есть session/project/placement/Node scope, audience, expiry, подпись,
rotation и проверка revocation. В новой итерации эти связи должны пережить
упрощение продукта.

Отдельно нужны credentials пользователя к Core, Node к Core, provider к
его API и tool runtime к конкретному upstream. Рекомендация — хранить
upstream secrets в выбранной доверенной runtime-boundary, передавать ссылки
или короткоживущие права, не включать секреты в события и snapshots.
OAuth credential должен быть связан с точной integration identity и endpoint;
смена URL не должна молча переиспользовать токен.

В T3 scoped MCP credential связан с конкретным владельцем provider session.
Полезный инвариант для Uprava: поздний cleanup старого подключения не может
отозвать credential уже созданной замены. Поэтому revoke/detach должны
проверять lease ID и generation владельца, а не только имя session или tool.

В текущем [refresh_mcp_access](../../../../crates/uprava-node/src/runtime/managed_provider.rs)
lease rotation блокируется при активном turn или interaction и заменяет
provider process через resume. Значит, отзыв и обновление доступа имеют
цену для живой сессии. Во второй итерации следует явно выбрать: стабильный
локальный broker с актуальной проверкой прав при каждом вызове либо
ограниченное обновление adapter между turn. Нельзя обещать произвольное
hot-reload credentials, если native protocol его не поддерживает.

ToolHive стоит рассматривать как заменяемый исполнитель MCP transport и
workload lifecycle. Core сохраняет пользовательскую policy и session scope.
Его включение не переносит автоматически правила Uprava в ToolHive.
Нужно явно определить точку enforcement: для первого среза возможна проверка
в Core при закрытом downstream пути без обхода. При делегировании проверки
ToolHive нужны доставка policy и проверка её версии.

По [разбору ToolHive](09-toolhive-control-implementation.md) особенно важно:
authz и registry policy не становятся строгими автоматически; остановка
remote proxy не отменяет удалённые effects; встроенная санитарная обработка
телеметрии не заменяет нашу redaction policy для вложенных структур.
Отзыв доступа должен запрещать новые вызовы немедленно на доступной границе;
поведение уже начатых вызовов описывается отдельно, с учётом возможностей
upstream. Отмена не означает rollback.

## Что брать и в каком порядке

| Приоритет | Переносимый подход | Источник | Цена и ограничение |
| --- | --- | --- | --- |
| P0 | Узкий adapter одного provider с явными capabilities и ownership | T3 + текущий Managed Uprava | Version pin и обработка изменений native API |
| P0 | Durable принятие input, receipt, idempotency и отказ при конфликте | OpenCode + outbox Uprava | DB-транзакции; внешний эффект требует отдельной гарантии |
| P0 | Supervisor клиента, согласованные snapshot/cursor и gap recovery | T3 + OpenCode | Отдельный state machine и bounded cache |
| P0 | Approval/input как durable interaction текущего attempt | T3 + Uprava | Корреляция native IDs, expiry и гонки ответа |
| P0 | Один scoped внешний tool с проверкой при discovery и execution | OpenCode + ToolHive + Uprava | Версионированная binding, понятные ошибки и отзыв |
| P0 | Явные состояния потери runtime и неопределённого tool effect | Сопоставление трёх реализаций | Более сложный UX, зато без ложного успеха и опасного retry |
| P1 | Несколько provider instances и remote endpoints | T3 | Разные trust/credential/lifecycle profiles |
| P1 | Динамический каталог и обновление bindings | OpenCode + ToolHive | Инвалидация, policy/schema generations, совместимость adapters |
| P1 | Замена либо добавление tool-runtime backend | ToolHive boundary | Дополнительная конфигурация и эксплуатация |

P0 означает необходимую часть первого сценария, P1 — расширение после его
приёмки. Это не просьба сейчас запускать эти системы или делать прототипы.
Текущее исследование завершается описанием реализации и проектных выводов.

Для перехода к разработке достаточно трёх коротких ADR: ownership и
deployment profile; session/command/event/recovery contract; tool binding,
enforcement и credential lifecycle. В каждом нужно зафиксировать также
отрицательные случаи: старая Node, старый approval, revoked tool, изменённая
схема, потерянный ответ после side effect. Они проверяют именно границы,
которые легко потерять при упрощении.

Из референсов не следует необходимость менять Rust/React, воспроизводить
Effect-архитектуру, писать собственный model loop или сразу строить
