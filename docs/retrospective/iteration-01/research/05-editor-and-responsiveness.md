# Редактор и отзывчивость рабочей поверхности

Первый кандидат для проверки — сохранить React и Monaco, изменив владение
буфером, обновления UI и жизненный цикл моделей. Это рекомендация по порядку
исследования, а не установленное решение: текущая причина задержек не
измерена. Замена editor engine до такого измерения может сохранить проблему
интеграции и добавить миграцию.

Дата исследования — 3 октября 2026 года. Основания: опыт владельца, выбранные
участки текущего frontend и первичные документы редакторов. Численные
latency-требования ниже являются предлагаемыми бюджетами следующего
эксперимента; это не результаты тестирования текущей версии.

## Что уже известно

Владелец считает редактор полезным, но недостаточно отзывчивым. В
[текущей реализации](../retrospective/04-ux-and-editor.md) у Monaco model и
view связанный lifecycle; переключение файла и уход с поверхности могут
пересоздавать model. Изменения текста проходят через общий draft context.
Это конкретные точки для профилирования, но не доказанный источник всей
задержки. Локальный ввод и ожидание сетевого read/save нужно измерять отдельно.

[Документация Monaco](https://github.com/microsoft/monaco-editor/blob/main/README.md)
различает model, которая хранит текст и историю, и editor view. URI задаёт
идентичность model, а dispose освобождает её ресурсы. Это позволяет исследовать
долговечные модели открытых документов отдельно от отображаемой панели.
Monaco также не является полным VS Code с совместимым extension ecosystem.

[Руководство CodeMirror](https://github.com/codemirror/website/blob/main/site/docs/guide/index.md)
описывает state, transactions, view и composition extensions. Оно даёт
альтернативную модель интеграции, но не доказывает, что CodeMirror быстрее в
нашем workflow. Сравнивать нужно одинаковые файлы, функции и сетевые условия.

[VS Code Remote Development](https://code.visualstudio.com/docs/remote/remote-overview)
размещает workspace execution на удалённой стороне и оставляет клиентский
интерфейс локально. Полезный принцип для Uprava — ввод не должен зависеть от
завершения remote operation. Это не требует копировать всё устройство IDE.

## Что сравнивать

| Вариант | Проверяемая польза | Цена и критерий отказа |
| --- | --- | --- |
| Monaco с отдельным хранилищем моделей | Сохранение undo/view state, быстрый возврат в документ, меньше работы React на keystroke | Память, eviction, cleanup; отказаться от конкретной схемы, если профиль не показывает выигрыша |
| CodeMirror с эквивалентным набором функций | Иная композиция editor state и extensions | Повторная интеграция diagnostics/diff/languages; не выбирать по размеру demo |
| Узкий просмотр и diff плюс внешний editor | Быстрый первый cloud-agent workflow без собственного полноценного IDE | Переключение приложений, настройка удалённого доступа, ограничения мобильного клиента |

Варианты не взаимоисключающие на уровне продукта: лёгкая коррекция может
оставаться встроенной, а глубокая работа — открываться во внешнем редакторе.
Такое сочетание требует проверки удобства на целевом сценарии.

## Предлагаемая модель данных

Сеть обслуживает загрузку, сохранение и сверку версии. Локальный buffer
обслуживает набор текста, курсор и undo. Состояния `clean`, `dirty`, `saving`,
`conflict` и `offline` видимы и не подменяются успешным optimistic toast.

Для первого одиночного сценария достаточно проверить сохранение относительно
прочитанной версии. Изменение файла агентом не должно молча затирать draft
пользователя. CRDT и синхронное совместное редактирование не вводятся без
отдельного требования. Существующую защиту expected-content нужно сохранить
при любом исследуемом варианте.

Предлагаемый ключ model включает workspace identity и нормализованный путь,
чтобы одинаковые пути на разных нодах не разделяли текст. Размонтирование view
не обязательно завершает жизнь model; закрытие документа и eviction должны
иметь явные правила для dirty state.

## Протокол измерения

Профиль выполняется на production build, отдельно от Vite dev mode. Фиксируются
commit, версии браузера и editor, CPU, размеры файлов, число открытых
документов, cache state и параметры сети. Fake API позволяет изолировать
frontend, реальный remote Node проверяет полный путь. Результаты этих двух
стендов не смешиваются.

| Метрика | Граница измерения | Предлагаемый стартовый бюджет |
| --- | --- | --- |
| Локальный ввод | Событие ввода → следующий отображённый кадр | p95 до 50 мс на согласованном desktop-профиле |
| Переключение уже загруженного файла | Команда → готовый buffer и курсор | p95 до 100 мс |
| Отображение provider event | Получение на клиенте → видимое изменение | p95 до 100 мс, отдельно от inference |
| Открытие незагруженного файла | Команда → пригодный для редактирования buffer | Измерить frontend и remote fetch отдельно; целевой бюджет выбрать после baseline |
| Сохранение | Команда → подтверждение durable write либо conflict | Не скрывать сетевую задержку; UI ввода остаётся доступным |

Эти бюджеты — предложение для review, не отраслевой стандарт. Нагрузочные
сценарии: небольшие и крупные текстовые файлы в допустимом лимите, длинная
история чата, одновременный stream и редактирование, RTT 0/50/150 мс, reconnect,
изменение файла агентом. Для p95 нужен достаточный набор повторов; несколько
ручных кликов не дают устойчивой оценки.

Сначала измеряется существующий путь, затем меняется одна переменная:
сохранение model между переключениями либо ограничение React updates. По
результатам выбирается необходимость сравнения engine. Отдельный тест
сохранности текста обязателен даже при улучшении latency.

## Вывод для первого среза

Полноценный встроенный editor не является обязательным условием первого
релиза панели. Нужен удобный способ проверить результат агента и, при
необходимости, внести коррекцию. Решение о глубине встроенного редактора
принимается после сравнения конкретных сценариев. В
[экспериментах](experiments.md) отдельно отмечено, какие проверки выполнены и
какие UX-гипотезы остаются открытыми.
