# Безопасность первого production развёртывания

Вывод исследования: безопасность нужно принимать для конкретного окружения и
сценария. Современный интерактивный протокол не снимает обязанность защищать
доступ к process, workspace и credentials. Рекомендация для новой итерации —
узкий production-профиль с явной моделью угроз до расширения возможностей.

Дата чтения внешних источников — 3 октября 2026 года. Это проектирование
требований на основе источников и текущей реализации, не penetration test,
сертификация или подтверждение готовности существующего deployment.

## Что дают внешние источники

[OWASP ASVS 5.0.0](https://owasp.org/projects/asvs) предоставляет версионируемые
требования к проверке web-приложений. Для Uprava полезен его подход «контроль →
проверка → доказательство». Номер ASVS-требования нужно сохранять вместе с
версией. Соответствие уровню ASVS в этой работе не оценивалось.

[OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
разделяет защищённый транспорт, проверку Origin, authentication и
authorization каждого сообщения. Установленное соединение не означает
безусловное право на все действия. Важны окончание сессии, лимиты сообщений и
журналирование без чувствительного содержимого. Эти требования относятся к
выбору real-time транспорта, а не только к обычным HTTP routes.

[MCP Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
описывает риски token passthrough, confused deputy, SSRF и неверных OAuth
redirects. Для будущего каталога инструментов это основание разделять
идентичность клиента, права на конкретный tool и downstream credential.
Единый интерфейс tools не должен становиться универсальным прокси привилегий.

У референсов есть собственные trust assumptions. Например, исследование
[T3 Code и OpenCode](01-reference-systems.md) не доказывает изоляцию
враждебных проектов друг от друга. Их удобство не является security acceptance
для облачных нод Uprava.

## Предлагаемый первый профиль

Рабочая рекомендация, требующая фиксации перед реализацией: один владелец,
выделенные управляемые cloud nodes, закрытая регистрация, один provider,
доступ из браузера через HTTPS. Профиль поддерживает реальные production
машины, но не обещает multi-tenant SaaS или безопасное размещение
взаимно недоверенных клиентов на одной OS.

При этом содержимое репозитория, ответы инструментов и вывод агента остаются
недоверенными. Даже единственный оператор может открыть чужой репозиторий или
получить prompt injection через внешний tool. Для действия проверяются
полномочия, а не убедительность текста агента.

Если реальная задача требует разделения команд, tenant-ов или недоверенных
пользователей, это другой профиль: его нужно выбрать до построения auth и
sandbox, а не добавлять как косметическое расширение после первого релиза.

## Минимальная модель угроз и приёмка

Таблица ниже — предложенные требования Uprava, а не перечень уже найденных
уязвимостей. Владельцами проверок выступают соответствующие системные границы.

| Актив или граница | Возможный отказ | Требование и негативная проверка |
| --- | --- | --- |
| Browser → Core | Чужая сессия, CSRF, cross-origin control | Авторизация HTTP и streams; запрещённый Origin не получает канал; logout закрывает дальнейшие действия |
| Core → Node | Подмена или повторная регистрация ноды | Явное enrollment; уникальная identity; ротация и revoke; старый credential не возвращает доступ после reconnect |
| Session → workspace | Выполнение в другом проекте | Scope проверяется на Core и перед локальным действием на Node; traversal/symlink/подмена placement дают отказ |
| Agent process | Избыточные привилегии и доступ к host secrets | Подтверждённая effective policy; allowlist environment; лимиты filesystem/network/process; безопасного режима без реального enforcement нет |
| Approval → command | Повтор, просрочка, решение для другого turn | Привязка к identity/attempt/action; однократное применение; replay и late reply отклоняются |
| Инструмент → внешний сервис | Прокси чужих credentials | Отдельные audience/scope, минимальные полномочия и проверенный отзыв доступа |
| Plugin → system | UI вводит в заблуждение или вызывает привилегированное действие | Явные capabilities и lifecycle для bundled modules; изоляция внешнего недоверенного кода по выбранной модели угроз; extension не выдаёт себе права и не подменяет доверенное подтверждение Core |
| Events → UI | Повтор команды после потери ACK, неверный статус | Durable receipt, idempotency и recovery; reconnect не повторяет побочный эффект |
| Output → logs/artifacts | Утечка токенов, персональных данных | Redaction, bounded payload, разрешения на чтение trace; canary secret отсутствует в экспортируемых данных |
| Deployment → состояние | Потеря данных, неверный rollback | Backup/restore rehearsal; совместимость binary/config/state; наблюдаемый rollback |
| Доступность | Flood, зависший процесс, утечка ресурсов | Ограниченные очереди, deadlines и admission; нагрузка не блокирует stop/revoke |

Некоторые контрмеры уже есть в `0.2.26`; их состояние и ограничения описаны в
[ретроспективе безопасности](../retrospective/06-security-and-operations.md).
Повторное использование требует сверки контрактов, а не переписывания всех
проверок с нуля.

## Решения до выхода в production

1. Зафиксировать trust boundaries и политику действий агента, включая network
   egress. Неподдерживаемое ограничение обозначается явно, без safe label.
2. Выбрать локальный transport provider adapter по совместимости и границам
   доступа. Provider endpoint не выставляется наружу автоматически вместе с
   Web/Core. Версия и схема protocol проходят отдельную проверку.
3. Описать bootstrap, credential storage, rotation, revoke и recovery;
   проверить их на развёрнутой ноде с реальным провайдером.
4. Связать каждый production requirement с тестом и эксплуатационным
   действием. Не прошедший обязательный контроль блокирует выпуск выбранного
   профиля, а не скрывается в общем списке будущих улучшений.

Опубликованные первичные источники дают направления проверки. Надёжность
конкретной схемы proxy, OAuth, sandbox и provider подтверждается своим
end-to-end испытанием. Его воспроизводимые сценарии находятся в
[журнале экспериментов](experiments.md).
