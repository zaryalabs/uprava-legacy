# Итоги первой итерации Uprava

Итерация закрыта по решению владельца продукта. Её главный урок: ширина
реализации росла быстрее, чем качество повседневной работы. Следующая итерация
начинается с узкого сценария управления облачными агентами через отзывчивый
интерактивный чат и с определённой моделью безопасного развёртывания.

Этот пакет передаёт опыт новой команде или агенту: устройство системы, причины
решений, ограничения, современные альтернативы и основания для следующего
шага. Продуктовые идеи сохраняются; их наличие в каталоге не обязывает
реализовывать их в первом срезе.

## Главные выводы

1. Основной полезный сценарий следовало довести до удобного регулярного
   использования перед расширением платформы. Количество закрытых slices не
   заменяет проверку качества сценария.
2. Интерактивная Agent session, ограниченная Task и фоновый Job требуют
   разных контрактов. В финале итерации Managed runtime уже реализован;
   история `exec/resume` не описывает всё состояние `0.2.26`.
3. Rust и React получили положительную оценку владельца. Долгая компиляция
   требует измерения. Неудобный редактор требует исследования пути данных и
   жизненного цикла буфера. Оснований автоматически заменять стек нет.
4. Трейсинг, управление инструментами, плагины и артефакты остаются полезными
   идеями. Практическая пригодность MCP/ToolHive недостаточно проверена.
5. Модульность нужно пересмотреть через композицию действий, объектов и
   сервисов, сохраняя явные права и ответственность за состояние.
6. Production должен означать конкретный профиль эксплуатации и пройденные
   проверки. Локальная авторизация, наличие sandbox и успешные unit-тесты
   сами по себе не закрывают эту задачу.

## Как понимать доказательства

- **Опыт владельца** — реальное впечатление от работы, не инструментальный
  профиль производительности и не оценка всех пользователей.
- **Реализация** — подтверждённое чтением кода поведение. Наличие теста
  отдельно от результата его запуска.
- **Проверка** — выполненная команда или наблюдение с условиями и результатом
  в журнале экспериментов. Mock/fake-провайдер не равен реальному сервису.
- **Внешний источник** — прочитанная документация или код конкретного проекта;
  заявление автора проекта не считается нашим испытанием.
- **Гипотеза или рекомендация** — наш вывод, для которого указаны основания и
  условия подтверждения. Это не измеренный факт.

Исторический [аудит `0.1.8`](../../audit/audit-2026-07-09.md) полезен для
понимания пути проекта. Его findings нельзя автоматически переносить на
финальную реализацию. Аналогично отметка «выпущено» в
[релизах](../../releases.md) не доказывает удобство регулярного использования.

## Проверка пакета

Локальные Markdown links проверены `make docs-l`, синтаксис трёх Mermaid-схем
проверен parser; `make t` прошёл:
384 Rust-теста, 175 Web-тестов и 4 builder-теста. Также прошли три выбранных
browser E2E с mock Core. Полный `make c` остановился на dependency audit
существующего `rustls 0.23.40`; advisory и ограничения сетевой проверки
сохранены в [журнале](research/experiments.md). Это не успешный полный gate и
не live acceptance реального deployment.

## Перенос и хранение

Пакет рассчитан на самостоятельное чтение. Относительные ссылки за пределы
этой папки дают дополнительные доказательства в исходном репозитории. При
переносе одной папки сохраните доступ к указанному commit репозитория; при
потере такого доступа останется объяснение решений, но не их исходный код.
Внешние moving-ссылки снабжены датой чтения в реестре источников.

Секреты, credentials, рабочие журналы с личными данными и содержимое
`.local/context/` в пакет не включаются. Публикация во внешние сервисы не
выполнялась.
