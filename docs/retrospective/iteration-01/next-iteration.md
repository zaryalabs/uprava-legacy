# Рекомендации для следующей итерации Uprava

Первый срез — панель управления облачным агентом с живым чатом, понятными
разрешениями и безопасным развёртыванием. Сохраняется широкий продуктовый
замысел, но реализация расширяется только после подтверждённой пользы
текущего сценария. Это рекомендации по результатам ретроспективы и
исследования, не готовая спецификация новой системы и не календарный roadmap.

Основания: [опыт владельца](retrospective/01-product-and-lessons.md),
[текущая архитектура](retrospective/02-architecture-and-runtime.md) и
[современные референсы](research/01-reference-systems.md).

Углублённое основание для remote integration —
[разбор механизмов T3 Code, OpenCode и ToolHive](research/10-remote-agents-and-tools-for-v2.md).
Он содержит pinned source links, сквозные цепочки, сравнение с `0.2.26` и
отдельные рекомендации P0/P1. Практические запуски upstream в этот этап
исследования не входили.

Дополнение от 7 октября —
[DeepSeek Harness для v2](research/13-deepseek-harness-for-v2.md).
Он становится основным референсом модульности, расширяемого чата и developer
tools. Его сервисные seams и lifecycle адаптируются к Core/Node; существующее
исследование удалённых provider runtime остаётся основанием их интеграции.

## Что переносить

| Область | Рекомендация | Основание и условие |
| --- | --- | --- |
| Продуктовые идеи | Сохранить все группы в каталоге возможностей | Владелец считает большинство идей полезными; каталог не задаёт обязательный scope |
| Core и Node | Сохранить разделение control plane и локального execution | Ясные owner и границы доверия; конкретные сервисы и протоколы можно изменить |
| Rust и React | Оставить исходным выбором | Положительный опыт; измерять узкие места до смены технологий |
| Managed Agent | Взять финальный опыт и тестовые сценарии за основу | `0.2.26` уже имеет live adapter; проверить актуальную provider version и transport |
| Commands, events и recovery | Сохранить инварианты и переоценить сложность реализации | Commit до publication, idempotency и current attempt полезны независимо от framework |
| Клиентская синхронизация | Спроектировать отдельное владение connection, cursor и snapshot | Исследование T3/OpenCode показывает пользу отличия transport health от freshness |
| Модульность | Описать сервисы, dependencies, scopes, lifecycle owners и contributions одним контрактом | Harness показывает проверяемую композицию; bundled registry следует дополнить resource ownership и diagnostics |
| Редактор | Сначала проверить интеграцию; глубокий IDE scope отложить | Польза есть, но источник задержек не установлен |
| MCP и ToolHive | Сохранить кандидатами; провести реальную ограниченную приёмку | Недостаточно практического опыта, текущая и новая ревизии protocol различаются |
| Jobs и Tasks | Сохранить отдельные модели; не включать автоматически в первый релиз | Interactive session и bounded execution решают разные задачи |
| Trace | С первого среза сохранять действия, права и причины переходов | Расширенный граф и богатый UI добавлять по сценарию расследования |
| Developer tools | Маленький Session Inspector и причины неактивности модулей с первого среза | Общие event/registry projections; полный topology browser и debugger добавлять позднее |
| Dynamic UI, team/cloud, иные области | Вернуться после доказанного основного workflow | Их ценность не закрывает стоимость расширения и поддержания качества |

Переиспользование кода решается по модулю: контракт, тесты, coupling и цена
переноса. Решение начать итерацию заново не требует автоматически выбросить
весь код или скопировать существующий workspace целиком.

## Конкретные выводы из исходников референсов

1. У T3 Code взять разделение provider driver/instance, самостоятельный
   connection supervisor и scoped credentials; сохранить Web → Core → Node.
2. У OpenCode взять durable input admission до запуска, барьер между
   выполнением команды и видимостью проекции, защиту от устаревших tool bindings.
   Legacy remote path и новый local SessionV2 изучать раздельно.
3. У ToolHive взять явный lifecycle runtime, раздельные caller/upstream
   identities и admission каждого вызова. Production policy включается
   осознанно; catalog, discovery и proxy readiness её не заменяют.
4. Сохранить имеющиеся в Uprava leases, current-attempt checks и durable
   events. Добавить в контракт tools проверку версии/binding, показанной
   агенту, и явное состояние неизвестного исхода после потери ответа.
5. Отложить собственный LLM loop, миграцию сессий между Node, множество
   providers и сложный registry. Один provider и один управляемый внешний
   read-only tool достаточны, чтобы спроектировать нужные границы.
6. У Harness взять scoped registrations с владельцем, dependency lifecycle,
   удержание composition revision, расширяемые Chat nodes и trace provenance.
   Observer/Inspector читает те же данные, которые использует runtime.
7. Различить read-only diagnostics и developer execution. CDP Console,
   generated extensions и raw payload capture требуют своей runtime-boundary;
   первый production-профиль получает узкие контролируемые команды.

Следующие проектные документы — три коротких ADR: deployment и ownership;
session/command/event/recovery; tool binding/policy/credential lifecycle.
Контракт модульности описывает владельцев, dependencies, revisions,
contributions и introspection; его следует закрепить рядом с этими ADR.
Их содержание и компромиссы заданы в
[синтезе исследования](research/10-remote-agents-and-tools-for-v2.md).

## Узкий первый сценарий

Предлагается начать с одного provider и одного согласованного deployment
профиля. Пользователь входит в панель, подключает разрешённую ноду, выбирает
workspace, запускает сессию и выполняет несколько последовательных turn.
Он видит вывод и вызовы tools, отвечает на approval/input, может interrupt,
закрыть вкладку, вернуться и восстановить достоверное состояние. Результат
можно проверить через минимальное представление изменений и источников.

Включить один управляемый внешний read-only tool: показать его доступность,
выполнить scoped вызов, объяснить отказ и отозвать доступ. Это узкий пример
tooling в основном сценарии, без обязательного переноса полного каталога
интеграций и автоматического управления всеми зависимостями.

Полноценный редактор, произвольные пользовательские плагины, планировщик,
универсальная sandbox-платформа и team RBAC не являются предварительными
условиями этого сценария. Исключение возможно, если выбранный deployment
профиль сам требует соответствующей границы безопасности.

## Порядок работы и выходные условия

### Определение профиля

Зафиксировать, кто использует систему, где находится Core, кому принадлежат
ноды, какие репозитории считаются недоверенными и какие действия допустимы.
Рабочий кандидат — один оператор и выделенные ноды с закрытой регистрацией.
Multi-tenant профиль выбирается отдельно, если он нужен с первого дня.

Выход: короткий scope, trust diagram, модель угроз и проверяемые ограничения.
Безопасность не переносится целиком в «hardening после MVP».

### Вертикальный срез живой сессии

Соединить browser, Core, Node и реального provider на минимальном интерфейсе.
Ввести durable identity, команды, упорядоченные события, approvals и
interrupt. Проверить два turn, detach/reattach, reload, reconnect и потерю
process. Время inference измерять отдельно от реакции интерфейса.

Выход: сценарий воспроизводим, нет silent unsafe fallback, повтор команды
не повторяет эффект, UI явно различает active, blocked, reconnecting и lost.

### Приёмка эксплуатации и удобства

Развернуть выбранный профиль, проверить credential rotation/revoke,
негативные права, backup/restore, ограничения ресурсов и диагностируемые
ошибки. Провести регулярное использование владельцем на реальных задачах и
зафиксировать найденные неудобства. Период приёмки и latency-бюджеты определить
до испытания; прохождение unit-тестов их не заменяет.

Выход: согласованные обязательные проверки пройдены, блокирующие неудобства
устранены, оператор понимает как диагностировать и восстановить систему.

### Проверка модульных границ

Сделать trace viewer и read-only tool/capability inspector через минимальные
контракты, в которых registry служит также источником diagnostics. Описать
отсутствующую dependency, lifecycle owner, composition revision и причины
неактивности. Проверить отключение, несовместимую версию, отказ и отсутствие прав.
Результат может подтвердить bundled modules или необходимость extension host.

Выход: хотя бы два разных расширения используют общий контракт без обхода
policy и без специальных ветвей в ядре ради каждого расширения.

### Следующее расширение

Выбрать одну наблюдаемую потребность: редактор, Jobs, integration или Tasks.
Для неё заранее определить ценность, минимальный сценарий и критерии
готовности. Одновременно вести один новый продуктовый срез; исправления
качества основного сценария имеют приоритет.

## Открытые решения

| Решение | Что уже известно | Что закроет вопрос |
| --- | --- | --- |
| Конкретный production-профиль | Нужен безопасный доступ к cloud agents | Согласованная модель пользователей, нод и доверия |
| Provider version и локальный transport | App-server и ACP дают применимые контракты; текущая совместимость требует проверки | Version-pinned runtime probe и deployment acceptance |
| Глубина встроенного редактора | Monaco integration имеет проверяемые гипотезы | Профиль текущего пути и сравнение с внешним editor workflow |
| Runtime расширений | Нужны программируемые действия и изоляция прав | Два контрастных расширения, измерение цены lifecycle |
| MCP/ToolHive | Опыт недостаточен, protocol меняется | Один реальный tool: connect, scoped call, отказ, revoke, reconnect |
| Ускорение Rust | Жалоба подтверждена опытом, причина не измерена | Раздельные cold/warm/check/test/link timings на доступном стенде |

Подробные протоколы и выполненные проверки находятся в
[журнале экспериментов](research/experiments.md). Неизвестные результаты не
блокируют сохранение ретроспективы, но ограничивают окончательность выбора
архитектуры.

## Новый критерий готовности

Функция завершена, когда пользовательский сценарий работает с реальным
провайдером, понятен без знания реализации, укладывается в согласованные
бюджеты отзывчивости, имеет проверенные права, ошибки и восстановление, а
результат можно проверить. Известные ограничения описаны и приняты в рамках
профиля. Следующая фича начинается после такой приёмки текущей.

Код, тесты, документация и release tag остаются необходимыми свидетельствами,
но оценка готовности включает опыт использования. Этот критерий исправляет
основную ошибку закрытой итерации.
